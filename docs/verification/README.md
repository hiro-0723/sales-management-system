# 検証手順

## 1. 目的

繰り返し必要になる確認方法を、担当者やAIが変わっても再利用できる形で保存する。

## 2. 読み方

すべてを毎回読まず、変更内容に対応する手順だけを読む。正常条件が不明なら推測せず、設計書、Project Memory、コード、利用者判断から確定する。

## 3. 変更内容との対応

| 変更内容 | 最初に読む手順 |
|---|---|
| 文書・設定・GitHub保存 | `release-checklist.md` |
| Apps Script関数 | `apps-script-function-test.md` |
| Googleフォーム・画面 | `browser-screen-test.md` |
| LINE WORKS連携 | 公式仕様と実機で方法を確立後、専用手順を追加 |
| データ構造・移行 | 実施前に専用手順を作成 |

## 4. 共通項目

- 目的、対象、事前条件
- 操作、正常条件、異常条件
- 状態変更と許可
- 確認用データと復元
- ログ、画面、差分などの根拠
- 実施できない場合の依頼内容

## 5. 更新ルール

実作業で確認でき、再利用できる方法だけを追加する。推測した関数名、正常値、LINE WORKS仕様、一時状態は正式手順にしない。
