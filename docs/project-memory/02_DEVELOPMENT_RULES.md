# 開発ルール

## 1. 1ステップ＝1目的

1回の作業では説明できる1目的だけを扱う。新エージェントシステムv2への移行とLINE WORKS機能実装を同じStepへ混ぜない。

## 2. 変更前確認

- Project Memory、Roadmap、Git状態を確認する。
- 最新ベースラインとの差分、対象、影響、変更しない範囲を整理する。
- 未確定仕様が必要なら実装前に利用者へ確認する。
- 問題発生時は、設計変更より先にベースラインとの差分を調べる。

## 3. 既存設計の保護

- 既存設計書を正本とする。
- 既存ルール、既存変更、安定稼働中のモジュールを無断で削除・上書き・巻き戻ししない。
- 設計変更時は、変更理由、メリット、デメリット、影響範囲を説明する。
- `地域情報ID → PlanID → 訪問履歴ID → 紹介実績`の追跡線を維持する。
- 新機能は原則として専用モジュールへ分離し、既存モジュールと疎結合で接続する。

## 4. フォーム・シート・UI

- Googleフォーム本体は原則再構築しない。
- 構造変更が必要な場合は、新規フォームと切替計画を作り、既存フォームはバックアップとして保持する。
- 生データシートは直接編集しない。
- フォームは現場入力、シートは管理・確認、ダッシュボードは判断・振り返りに使う。
- LINE WORKS移行でも、UI都合で既存データ構造を先に変更しない。

## 5. ファイル変更

- リポジトリをコードの正本とし、Apps Scriptエディタで直接編集しない。
- 最小差分にし、曖昧な一括置換を避ける。
- 文字列や改行を変更した場合は差分を目視確認する。
- 一時調査関数は`Diagnostics.js`に置き、調査後に削除する。
- 秘密情報、認証情報、個人情報をコード、Project Memory、Gitへ含めない。

## 6. 構文・静的確認

- JavaScript：`node --check 対象ファイル.js`
- JSON：JSONパーサーで`appsscript.json`と変更したスキーマを確認
- シェル：`bash -n tools/start_chat.sh`
- Apps Script固有APIの実動作はローカル構文確認だけで完了扱いにしない。

## 7. テストと実機確認

- 正常経路、境界値、失敗時、既存動作への影響を確認する。
- 自動テストは現時点で未整備。再現可能な確認手順と正常条件を先に定める。
- Apps Scriptへ反映後、対象関数、ログ、保存先、再実行、必要なら画面を確認する。
- 確認用データは事前値を記録し、確認後に復元する。
- LINE WORKS連携の検証手順は、公式仕様と実機で確立後に追加する。

## 8. Git差分確認

```bash
git status --short --branch
git diff --check
git diff --stat
git diff
```

ステージ後は`git diff --cached --check`と詳細も確認する。想定外の変更があれば保存せず停止する。

## 9. 外部環境への反映

- 反映方法：`clasp push`。実際の運用コマンドと対象プロジェクトは反映前に再確認する。
- 対象環境：既存の営業管理システム用Apps Script
- 復元方法：直前のGitHub安定コミットとApps Scriptのバージョン・バックアップを確認してから定める。

外部反映、実データ変更、外部送信、権限変更、commit、pushは、対象、影響、復元方法を示して利用者の許可後に行う。

## 10. GitHub保存

- 必要な確認と実機確認を終えた安定地点だけを保存する。
- Phase・Step完了時は完成条件を確認し、Project Memoryを実態へ合わせる。
- `docs/verification/release-checklist.md`を使う。
- push後はローカルと`origin`の同期、作業ツリーを確認する。

## 11. 利用者への説明

結論を先に、変更、非変更、確認結果、未確認事項を分ける。確認依頼には開く場所、ファイル名と関数名、操作、正常条件、返してほしい根拠を含める。

## 12. 検証手順の更新

再利用可能な方法が実作業で確立したら`docs/verification/`へ追加する。推測したLINE WORKS仕様や一時状態は正式手順にしない。
